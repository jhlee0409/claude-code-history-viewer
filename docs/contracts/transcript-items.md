# Pure transcript item contract (TR3 child 1)

`buildTranscriptItems(flattened, membership, options)` consumes the **existing** `flattenMessageTree` result. It is not connected to `useMessageVirtualization` in this child. No existing render, navigation or capture path changes were made by the pure model itself. The producer-grounding correction to the **shared** classifier below does affect existing navigator kinds/prompts-only/outline, prompt jumps and minimap presentation; it is not a no-visible-change claim.

## Inputs and ownership

- `TurnMembership` is a read-only map of message UUID to ordinal or null. Missing and null both mean unknown. Every row gets its own lookup; no row inherits a numbered membership from the preceding display row.
- `turnStartUuids` optionally projects the turn index's ordinal to canonical start UUID. It outranks loaded-row heuristics. Lookup hits alone contain no start UUID, so without this metadata a partial turn's ID is provisional (`turn:<first-loaded-uuid>`). Its **block IDs do not change** when membership or start metadata arrives. This resolves the difference between EV1a's index and lookup response shapes without adding a backend requirement.
- Known memberships group only contiguous display segments. Unknown memberships use unnumbered temporary groups, divided by `isTurnStart`. An assistant-first segment is partial. The predicate excludes metadata, generated caveats/output, result-only records and main-view sidechains; subagent user prompts start turns. A slash-command invocation is a user turn, unlike its generated output (consistent with the existing prompt classifier). EV1a must share the verified predicate rules, but must not promote the ungrounded fallbacks below to producer guarantees.
- Ordering, command/stdout merging, rootless-page recovery, task/progress/operation grouping, date dividers and capture placeholders remain owned by flattening. Existing content pairing remains owned by `contentEntries`. Blocks retain position-free renderer source data; consumers must not derive new item positions from an old `originalIndex`.
- Result evidence is read only through `toolOutcome`, including the legacy single-call envelope adapter. Fallback/media/unknown values and grouped-row metadata stay available to the existing renderers.

### Owner decision: automated cycles, and remaining ungrounded fallbacks

- **Owner decision adopted:** Claude `<task-notification>` and complete Codex `<heartbeat>…</heartbeat>` user input start their own **automated** turns in the pure model. `TranscriptTurn.kind` is `human | automated | unknown`; unknown is used for a partial loaded window with no canonical start evidence, never guessed from assistant output. Subsequent tools/results and their summary counts belong to the automated turn, not the preceding human turn. Known membership still comes from the index (which must adopt this same cycle policy); no ordinal is invented.
- **Producer evidence:** Claude 2.1.x audit found 110 notification cycles with their own `promptId` and `origin.kind:"task-notification"`, 76 with tool calls. Codex 0.148–0.164 audit found 34 client heartbeat inputs with producer `item_completed {item.type:"UserMessage"}` events; a structural recheck found 34/34 complete closing heartbeat wrappers. These are **client-origin scheduler inputs recognized by Codex**, not Codex-generated injected-context tags or human prompts. Codex 0.164.0's pinned [heartbeat.rs L62–110](https://github.com/openai/codex/blob/6aaac694803004a63c6f393d153c96d22521a6b9/codex-rs/history/src/heartbeat.rs#L62-L110) reads one host-marked InputText and the exact scheduler envelope; [heartbeat_tests.rs L23–28](https://github.com/openai/codex/blob/6aaac694803004a63c6f393d153c96d22521a6b9/codex-rs/history/src/heartbeat_tests.rs#L23-L28) rejects trailing ordinary text, injected timestamp text and a bare heartbeat wrapper. This is reader/provenance evidence, not the external scheduler emitter. The frontend fallback mirrors the single-item shape (projected string or exactly one text block), UTF-8 byte + line-count budget ≤3600 (L78–82), exact newlines/field order, ASCII automation_id (1–128 bytes), timestamp character set (1–64 bytes), and optional single final LF (L87–101). Instructions remain opaque, including literal delimiter tags: the reader splits the first field separators and strips the final suffix, not the first closing heartbeat. Consequently concatenated complete envelopes can be parsed as one instruction body; the old negative expectation was contradicted by L88–91 and is now a reader-parity positive. `heartbeatBoundary.test.ts` covers these rules through classifier, outline/model and human-only display consumers. Structural recheck: all 34 local heartbeats have exactly one opening/closing marker, automation_id/current_time_iso/instructions fields, and no surrounding text. **Provenance is still a fallback:** only 20/34 carry `user.heartbeat`; four carry `user.text` and ten omit kinds. The backend drops that metadata, so preserving all 34 follows the existing owner policy, not exact host-origin recovery.
- Human-only navigator prompts and user-only transcript/display/export exclude these automatic cycles; all-messages retains them. Heartbeats use the existing generic `context` UI kind so they cannot be counted as typed prompts. Claude notifications keep their existing `agent-update` UI kind. No new visible label or i18n key is required now. The wiring child must render `turn.kind === "automated"` as a distinct automatic notification (planned Korean label `자동 알림`), localize the label in all five locales then, exclude automated turns from human-prompt counts, and use the model's separate summaries. The legacy outline remains independent of the model, but now uses the same automated-boundary decision: heartbeat and notification cycles are separate outline entries, with their own replies/tools and no automated work in adjacent human counts. Their headers reuse the existing localized agent-update label, not a numbered human-prompt label; only human outline turns contribute to prompt numbering/counts. Notification task payloads remain reachable in the opened automated entry. Unlike notification task blocks, the heartbeat header is not repeated in an activity child: heartbeat-only cycles have no children, while later reply/tool rows still form their normal activity child (`outline/automatedTurns.test.ts`, `MessageNavigator.outline.test.tsx`).
- **Tool-result siblings are UNGROUNDED:** `tool_result` plus text without `toolUseResult` currently starts a turn; result plus image/document can start a turn **in the main view too**, not only subagent forks. No siblings existed in 5,022 audited Claude result records. R7 characterizes the existing image fallback, not producer correctness; do not invent fork guarantees.
- **Attachment-only mid-turn prompts are uncovered:** five `attachment/queued_command` human prompts (`commandMode:"prompt"`, `humanTurn:true`, `origin.kind:"human"`), four stored only as attachments, are excluded by the user-type check. ## Output

`items` contains turn fragments plus unchanged-source divider/hidden items. Turns contain a source-ordered block list and a summary of calls, distinct recorded file targets, failed verdicts and unknown/unverified verdicts. Results paired into a call are source-position aliases, not extra calls.

A fragment has at most 24 display blocks; with `viewportHeight` and `estimateBlockHeight` it also splits before a block that would exceed three viewports. An individually oversized block remains indivisible. The first fragment owns `turnStart`; every fragment has part/parts and loaded-feed `posinset`. `setsize` is fragment count only when `complete` is explicitly true, otherwise -1. These fields are **not DOM/a11y integration**.

Only consecutive read/search calls whose adapter returns completed/succeeded fold, and only within one fragment of one turn. All other blocks break the run. The call ID is its original `${uuid}#${contentIndex}`; a run is `run:<first-block-id>`; a fragment is `<turn-id>:<first-block-id>`. Paired-result IDs also resolve to their call.

## Targets and expansion

`itemIndexForTarget(model, {messageUuid, contentIndex?} | {blockId})` is the sole public target resolver. It uses direct lookup maps, defaults to the message's first block, returns null when unavailable, and returns the owning displayed block plus the IDs required to reveal a folded run. It never mutates a model. `revealTargets` applies that same entry for search, anchors, focus and selection; capture mode opens every run. Hidden UUIDs are unavailable until the existing hide path restores them.

Expansion is retained by **all source block IDs** in a run. Pass the previous model to preserve expansion across splits/merges. An explicitly supplied empty `expandedBlockIds` closes previous expansion. Capture's all-open projection is temporary: it does not add run members to the retained set, so exiting capture with only `previous` restores the prior expansion. Explicit IDs and `revealTargets` (including result aliases) propagate retention to all run members even during capture, so a split before capture exits preserves both halves. Capture-only runs never propagate retention.

## Incremental ownership

Pass immutable message/group inputs and `previous` for incremental extraction. The row cache uses message UUID plus a structural renderer signature, excluding only top-level `originalIndex`. It includes merged command content, group entries/registries and outcome evidence, not the object references recreated by flattening. Unchanged renderer sources reuse block objects; unchanged turn segments reuse turn objects and their summaries by identity, including when preceding pages shift positional indexes. Changed content or group data invalidates blocks; membership/start metadata changes invalidate affected turns even when source blocks remain reusable. Shared registry Maps are serialized once per identity per build and interned by their complete structural content. Row signatures use small build-local registry tokens, avoiding repeated full-registry string copying/comparison while preserving equivalence across fresh Maps and invalidation across builds. Serialization work is O(L + R) for L leaders sharing R registry entries (canonical key sorting retains its sorting cost); lookup scans are linear in loaded blocks; this is not a constant-time append claim. Fragment coordinates/lookup positions and expansion projections are rebuilt without mutating the previous model.

Provisional turn IDs and their fragment IDs are **not durable anchors**. Later wiring must restore scroll, focus, search, capture and history through block/source IDs, preserve pixel offsets separately, and re-resolve after canonical metadata arrives. Persisting turn IDs would require a canonical-only or explicit migration policy.
